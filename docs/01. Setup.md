# 01 — Lab Setup

This document covers the environment build: network isolation and the Sysmon/Splunk telemetry pipeline. Everything downstream (attack simulation, detections) depends on this foundation being correct.

---

## I. Isolated and Secure Environment

### Virtual Machine Provisioning

Two VMs were provisioned in VMware Workstation:

- **Kali Linux** — attacker platform (Nmap, Hydra, Metasploit/msfvenom)
- **Windows 10** — victim host, also running Splunk Enterprise as the local SIEM

### Network Isolation — NAT to LAN Segment

By default, VMware assigns new VMs to a **NAT** adapter, which routes traffic through the host machine's network stack. This is unsuitable for an attack simulation lab — malicious traffic (scans, brute-force attempts, payload callbacks) should never have a path to the host network or the internet.

Both VMs' network adapters were reconfigured from NAT to a dedicated **VMware LAN Segment** — a private virtual switch that only the VMs attached to it can see. This provides full isolation: no NAT translation, no internet egress, no visibility from the host's real network.

**Steps taken:**
1. VM Settings → Network Adapter → Custom → LAN Segment
2. Created a new LAN Segment and attached both VMs to the **same** segment (segment name must match exactly on both VMs — a mismatch here results in traffic never reaching the other host, even though both machines appear "connected")
3. Verified adapter status as connected on both VMs

### Static IP Addressing

Both hosts were assigned static IPs on the same subnet to ensure addresses remain consistent across reboots (DHCP on an isolated segment would otherwise leave hosts unable to find each other reliably):

| Host | IP Address | Role |
|---|---|---|
| Kali Linux | 192.168.10.33 | Attacker |
| Windows 10 | 192.168.10.34 | Victim / SIEM |

- **Windows:** configured via Control Panel → Network Settings → IPv4 Properties (persists automatically across reboots)
- **Kali:** configured via `nmcli` rather than a temporary `ip addr add`, since the latter does not survive a reboot:
  ```bash
  nmcli con mod "Wired connection 1" ipv4.addresses 192.168.10.33/24
  nmcli con mod "Wired connection 1" ipv4.method manual
  nmcli con up "Wired connection 1"
  ```

### Connectivity Verification

Bidirectional connectivity was confirmed with ICMP and ARP resolution:

```bash
# Kali
ping 192.168.10.34
arp -a
```
```
# Windows (cmd)
ping 192.168.10.33
arp -a
```

A successful ARP resolution (a real MAC address returned for the peer's IP, not `<incomplete>`) confirms both hosts are correctly on the same LAN Segment at Layer 2, prior to any Layer 3/4 troubleshooting.

## II. Install and Configure Sysmon and Splunk Enterprise

### Splunk Enterprise Installation

Splunk Enterprise was installed directly on the Windows 10 victim host. Running the SIEM on the same host it monitors is not standard production practice, but is a reasonable simplification for a single-victim home lab — it also removes the need for a Universal Forwarder, since Splunk can read local Windows Event Log channels directly.

<!-- SCREENSHOT: Splunk Enterprise installed, login screen or home page -->

### Sysmon Installation

[Sysmon](https://learn.microsoft.com/en-us/sysinternals/downloads/sysmon) (Sysinternals) was installed to provide endpoint telemetry beyond what default Windows auditing captures — specifically process creation, network connections, and registry modifications, all of which are required for later detections in this project.

Sysmon was installed using the **SwiftOnSecurity** community configuration, which enables a comprehensive, well-tuned ruleset out of the box (the default Sysmon install with no config file only logs process create/terminate events, and omits network and registry visibility entirely — a gap that was identified and corrected during this build):

```
sysmon64 -i -accepteula
sysmon64 -c sysmonconfig-export.xml
```

Configuration was verified with:
```
sysmon64 -c
```
Expected output confirms `Network connection: enabled`, `Registry: enabled`, and a non-zero rule count.

<!-- SCREENSHOT: sysmon64 -c output showing full ruleset active -->

### Registering Sysmon as a Splunk Data Input

Sysmon's event channel (`Microsoft-Windows-Sysmon/Operational`) is a custom "Applications and Services" log and does not reliably appear in Splunk's GUI data-input picker. It was registered directly via `inputs.conf`:

**File:** `C:\Program Files\Splunk\etc\system\local\inputs.conf`
```ini
[WinEventLog://Microsoft-Windows-Sysmon/Operational]
disabled = 0
index = main
renderXml = 0
```

Splunk was restarted to apply the change:
```
cd "C:\Program Files\Splunk\bin"
splunk restart
```

<!-- SCREENSHOT: inputs.conf contents -->

### Ingestion Validation

Before proceeding to attack simulation, ingestion was confirmed live in Splunk:

```spl
index=main sourcetype="WinEventLog:Microsoft-Windows-Sysmon/Operational" earliest=-15m
| stats count by EventCode
```

A non-empty result — with EventCode 1 (Process Create), 3 (Network Connection), 5 (Process Terminate), and 13 (Registry Event) all present — confirms the full telemetry pipeline is operational and ready for the attack simulation phase documented in `02-data-validation.md` onward.

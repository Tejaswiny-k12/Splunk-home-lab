# 03. Network Scanning

## Overview

With Sysmon ingestion into Splunk confirmed (see [02. Data validation.md](02.%20Data%20validation.md)), the next step in the lab is to generate a known, attributable event on the network — a port/service scan against the Windows victim machine — so that its corresponding telemetry can later be located and correlated in Splunk.

Sysmon records every inbound and outbound TCP/UDP connection on the monitored host (`EventCode 3`), which means a scan launched from the Kali attacker machine against the Windows target should show up as a burst of connection events once it reaches Splunk. Generating this activity deliberately, in an isolated lab segment, gives a clean, timestamped reference point to validate detection logic against in later stages (e.g. [04. Malware execution.md](04.%20Malware%20execution.md), [07. Attack chain correlation.md](07.%20Attack%20chain%20correlation.md)).

## Objective

- Enumerate open ports, running services, and the OS fingerprint of the Windows victim machine from the Kali attacker machine.
- Run a secondary scan to flag any known vulnerable services on the target.
- Use the resulting timestamps and ports later in Splunk to confirm that the scan activity was captured by Sysmon.

## Tooling

**Nmap** (Network Mapper) is used from the Kali attacker VM to scan the Windows victim VM over the isolated LAN segment set up in [01. Setup.md](01.%20Setup.md).

### 1. Service & OS Detection Scan

```bash
nmap -sS -sV -O 192.168.10.34
```

| Flag | Purpose |
|---|---|
| `-sS` | TCP SYN ("stealth") scan — probes ports without completing the full TCP handshake. |
| `-sV` | Service/version detection — attempts to identify the software and version listening on each open port. |
| `-O` | OS fingerprinting — attempts to identify the target's operating system from TCP/IP stack behavior. |

**Result:**

![Nmap service, version, and OS detection scan against the Windows victim host](images/network-scanning-nmap-sS-sV-O.png)

*The scan identifies six open ports on the target — including `135` (MSRPC), `139`/`445` (NetBIOS/SMB), `5432` (PostgreSQL), and `8000`/`8089` (Splunk's own web and management ports) — and correctly fingerprints the host as Windows 10.*

### 2. Vulnerability Scan

```bash
nmap --script vuln 192.168.10.34
```

This runs Nmap's `vuln` script category, which checks open services against a set of known vulnerability signatures (e.g. legacy SMB CVEs).

**Result:**

![Nmap vulnerability scan against the Windows victim host](images/network-scanning-nmap-vuln-script.png)

*The vulnerability scripts report inconclusive/negative results for the tested SMB CVEs (`ms10-061`, `ms10-054`, `CVE-2012-1182`) on this target — expected, since the lab VM is a modern Windows 10 build rather than a deliberately vulnerable legacy image. The scan is still useful as a baseline step in the methodology and as a timestamped event to locate later in Splunk.*

## Why This Step Matters for Detection Engineering

From a SOC analyst's perspective, this step is not about the scan results themselves — it's about understanding **what a reconnaissance scan looks like in the log source you are monitoring**. Specifically:

- A SYN scan against multiple ports in a short time window produces a recognizable pattern of `EventCode 3` (network connection) events in Sysmon, all sharing the same source IP and occurring in rapid succession.
- Correlating the **timestamp** of the Nmap scan with Sysmon `EventCode 3` events for the Kali attacker IP is a useful exercise for validating that network reconnaissance is visible in the pipeline before relying on it to detect real activity later.
- This also previews one of the limitations of endpoint telemetry: Sysmon on the **target** host sees the scan as a series of inbound connections, but it has no native concept of "this is a port scan" — that pattern has to be recognized through SPL logic (e.g. counting distinct destination ports per source IP in a short time window), not read directly off a single event.

## Outcome

This step confirms:

1. The isolated lab network allows the Kali attacker machine to reach and scan the Windows victim machine.
2. A concrete, timestamped reconnaissance event now exists in the environment, with known source IP, destination IP, and ports involved.
3. This scan can later be cross-referenced against the Sysmon `EventCode 3` data flowing into Splunk, reinforcing the role of network-connection telemetry in building a fuller attack timeline.

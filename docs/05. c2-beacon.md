# 05. C2 Beacon Detection

## Overview

Following the execution detection in [04. Malware execution.md](04.%20Malware%20execution.md), the next step is to confirm — from Splunk, rather than from the host itself — that the malicious process actually communicated outbound to the attacker-controlled machine on the isolated lab segment.

The `netstat` output captured directly on the victim earlier showed a single, point-in-time snapshot of an established connection on port `4444`. The goal here is to reconstruct that same connection activity centrally in Splunk, using Sysmon's network-connection telemetry (`EventCode=3`), and to see it as a *pattern* over time rather than a single snapshot.

## Objective

- Confirm that the suspicious process (`Resume.exe`) made outbound network connections to the attacker IP (`192.168.10.33`), matching what was observed locally via `netstat`.
- Establish the destination port(s) used, to corroborate the earlier finding of port `4444`.
- See the beaconing behavior as a time-series, which is useful for distinguishing a single one-off connection from a C2 channel that reconnects repeatedly.

## SPL Query

```spl
index=main sourcetype="WinEventLog:Microsoft-Windows-Sysmon/Operational" EventCode=3 DestinationIp="192.168.10.33"
| table _time, Image, DestinationIp, DestinationPort
```

| Clause | Purpose |
|---|---|
| `EventCode=3` | Filters to Sysmon's network-connection events only. |
| `DestinationIp="192.168.10.33"` | Narrows to connections headed to the known attacker-controlled host in the lab segment. |
| `table _time, Image, DestinationIp, DestinationPort` | Surfaces the fields needed to confirm when the connection occurred, which process made it, and which port was used. |

## Interpreting the Pattern

This small result set is more informative than it first appears:

- **Same process, same destination, same port, every time.** This consistency is a strong indicator of a configured C2 channel rather than incidental/background traffic — a legitimate application rarely calls out to the exact same non-standard port with no DNS resolution involved.
- **Repeated connections roughly 20–40 minutes apart.** This spacing is consistent with a session being re-established (the lab's listener being reconnected to) rather than a single sustained session — in a real environment this re-connection pattern over hours or days is a classic beaconing signature.
- **Port 4444 with no associated service.** Cross-referencing against the Nmap scan results in [03. Network scanning.md](03.%20Network%20scanning.md) confirms this port was not among the services legitimately running on the victim (`msrpc`, `netbios-ssn`, `microsoft-ds`, `postgresql`, Splunk's web ports) — it only appears once the malicious process is active, tying it directly to that process rather than to normal host behavior.
- **Corroborates the host-level evidence.** This Splunk-based detection independently confirms the single `netstat` snapshot taken on the host in the previous stage, demonstrating why centralized log aggregation is valuable: the same finding is now reproducible and query-able without needing live access to the endpoint.

## Analyst Next Steps

1. **Treat `192.168.10.33` and port `4444` as indicators of compromise (IOCs)** and search across all hosts in the environment for the same destination, to scope whether other machines are also beaconing out.
2. **Correlate the connection timestamps against the process-creation timestamps** from [04. Malware execution.md](04.%20Malware%20execution.md) — each outbound connection should align closely with (or follow shortly after) a `Resume.exe` execution event.
3. **Check whether the destination IP is internal or external** in a production setting — here it is internal to the lab segment by design, but in a real investigation an unexpected external destination would raise the severity significantly.
4. **Feed this IOC into blocking controls** (firewall/EDR network rule) to cut off the channel while the broader investigation continues.

## Outcome

This stage confirms:

1. The malicious process's network activity is fully visible and reproducible in Splunk via Sysmon `EventCode=3`, independent of host-level tools.
2. The connection pattern (same destination, same port, repeated over time) is consistent with an active C2 channel rather than a one-off event.
3. This network evidence, combined with the process-creation evidence from stage 04, forms two of the three pillars needed for the full attack timeline — the third being persistence, covered next in [06. Registry-persistence.md](06.%20Registry-persistence.md).

# 06. Registry Persistence Analysis

## Overview

After confirming execution ([04. Malware execution.md](04.%20Malware%20execution.md)) and an active C2 channel ([05. c2-beacon.md](05.%20c2-beacon.md)), the next question in a real investigation is always: **did the attacker establish persistence?** A process that runs once and a connection that beacons out are serious, but if nothing survives a reboot or logoff, the exposure window is limited. This stage checks the host's `Run` key — one of the most common Windows persistence locations — for evidence that `Resume.exe` (or a derivative of it) re-launches itself automatically.

## Objective

- Query Sysmon `EventCode=13` (registry value set) to see what registry write activity occurred on the host during the incident window.
- Directly inspect the `HKCU\Software\Microsoft\Windows\CurrentVersion\Run` key on the victim to check for an unauthorized autorun entry.
- Determine, from the evidence actually collected, whether persistence was established — rather than assuming it was.

## Direct Registry Check on the Host

```
C:\Users\tejas\Downloads>reg query "HKCU\Software\Microsoft\Windows\CurrentVersion\Run"
```

![reg query output showing the contents of the Run key](images/persistence-registry-runkey.png)

**Result:**

| Value Name | Data |
|---|---|
| `OneDrive` | `C:\Users\tejas\AppData\Local\Microsoft\OneDrive\OneDrive.exe /background` |
| `MicrosoftEdgeAutoLaunch_C0752BA0937E9DC93E60DD098CFF51F4` | `C:\Program Files (x86)\Microsoft\Edge\Application\msedge.exe --no-startup-window --win-session-start` |

**Finding:** both entries in the `Run` key are legitimate, expected Windows/Microsoft Edge autostart entries. **No entry referencing `Resume.exe` or any unrecognized binary is present.** Based on this check alone, the malicious process did not add itself to this specific autorun location during this lab run.

## SPL Query: Registry Activity on the Host

```spl
index=main sourcetype="WinEventLog:Microsoft-Windows-Sysmon/Operational" EventCode=13
| table _time, TargetObject, Details, Image
```

| Clause | Purpose |
|---|---|
| `EventCode=13` | Filters to Sysmon's "Registry value set" events — triggered whenever a monitored registry value is created or modified. |
| `table _time, TargetObject, Details, Image` | Surfaces which registry key was touched, what value was written, and which process made the change. |

## Results

![Splunk results showing 540 matching EventCode=13 events, dominated by routine Windows registry activity](images/registry-persistence-splunk-eventcode13.png)

This broad query returned **540 matching events** over the capture window — far more than can be reviewed line by line, and dominated by routine, benign Windows background activity:

| TargetObject (pattern) | Image | Assessment |
|---|---|---|
| `HKLM\...\WinlogonNotifications\Components\TrustedInstaller\Events` | `TrustedInstaller.exe` | Routine Windows servicing component — not attacker-controlled. |
| `HKU\...\AppCompatFlags\CompatibilityAssistant\Store\...\Resume.exe` | `svchost.exe` | Windows' **Program Compatibility Assistant** logging that it evaluated `Resume.exe` — this *references* the suspicious binary, but it is Windows' own compatibility telemetry, not a persistence mechanism. |

## Interpreting an Inconclusive Result — Why This Matters

This stage is deliberately included to show something important about real detection work: **not every hypothesis is confirmed by the data, and the SOC workflow has to handle that honestly.**

- The broad `EventCode=13` query is too noisy to use as a standalone detection — at 540 events, it would need further filtering (e.g. restricting `TargetObject` to known autorun/persistence paths such as `*\Run\*`, `*\RunOnce\*`, `*\Services\*`) to be actionable.
- The one row that does reference `Resume.exe` (the AppCompat entry) is a **side effect of Windows observing the binary run**, not evidence that the binary modified the registry for persistence.
- The direct `reg query` check against the specific `Run` key — the most targeted and reliable check — came back clean.

**Conclusion for this lab run:** based on the evidence collected, this particular execution of `Resume.exe` did not establish `Run`-key persistence. This is a legitimate and common outcome — not every payload includes a persistence mechanism, and some persistence techniques (scheduled tasks, services, WMI event subscriptions, `RunOnce`, startup folder) live outside the `Run` key entirely.

## Analyst Next Steps

Since this specific check came back negative, a thorough investigation does not stop here — it broadens the search:

1. **Narrow the SPL query to known persistence paths specifically:**
   ```spl
   index=main sourcetype="WinEventLog:Microsoft-Windows-Sysmon/Operational" EventCode=13 TargetObject="*\\Run\\*" OR TargetObject="*\\RunOnce\\*"
   ```
2. **Check Sysmon `EventCode=12`** (registry key/value create or delete), which can catch persistence mechanisms that *create* a new key rather than *set* a value on an existing one.
3. **Check scheduled tasks and services** — `schtasks /query` and `sc query`, or the corresponding Sysmon/Windows Event Log sources, since these are equally common persistence vectors outside the registry.
4. **Re-verify after further dwell time** — some payloads wait before establishing persistence to evade detection tooling.
5. **Document the negative finding** explicitly in the incident timeline — an absence of persistence is a meaningful, reportable fact, not something to omit.

## Outcome

This stage demonstrates:

1. How to query and interpret Sysmon registry telemetry (`EventCode=13`) for persistence indicators.
2. That a clean, well-scoped direct check (the `Run` key query) can quickly resolve a specific hypothesis, even when a broad SPL query returns too much noise to review manually.
3. That documenting a negative result correctly is as much a part of the analyst's job as flagging a positive one — this feeds directly into the complete, honest attack timeline assembled next in [07. Attack chain correlation.md](07.%20Attack%20chain%20correlation.md).

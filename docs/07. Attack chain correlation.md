# 07. Attack Chain Correlation

## Overview

The previous three stages each looked at one data source in isolation:

- [04. Malware execution.md](04.%20Malware%20execution.md) — process creation (Sysmon `EventCode=1`)
- [05. c2-beacon.md](05.%20c2-beacon.md) — network connections (Sysmon `EventCode=3`)
- [06. Registry-persistence.md](06.%20Registry-persistence.md) — registry writes (Sysmon `EventCode=13`)

Individually, each of these is a useful detection. But a SOC analyst's real job is **correlation**: pulling all of this telemetry together into a single, time-ordered view so that a sequence of individually-plausible events becomes a legible story — "this binary ran, then it talked to this IP, then this registry activity happened nearby" — which is far more convincing (and far more useful for scoping impact) than any single event on its own.

## Objective

- Build one SPL query that pulls every event tied to the suspicious binary (`Resume.exe`) **or** to registry run-key activity, across all relevant Sysmon event codes.
- Sort the combined results chronologically to reconstruct the attack timeline in the order it actually happened on the host.
- Use that timeline to distinguish genuinely malicious activity from incidental, unrelated Windows background noise that happens to match the filter.

## SPL Query

```spl
index=main sourcetype="WinEventLog:Microsoft-Windows-Sysmon/Operational" Image="*Resume.exe*" OR TargetObject="*\\Run\\*"
| table _time, EventCode, Image, TargetObject, Details, CommandLine, DestinationIp
| sort _time
```

| Clause | Purpose |
|---|---|
| `Image="*Resume.exe*" OR TargetObject="*\\Run\\*"` | Pulls in every event where the suspicious binary was the subject (any event code) **or** where any process touched a `Run` autorun key — casting a wide enough net to catch persistence attempts even from processes other than `Resume.exe` itself. |
| `table _time, EventCode, Image, TargetObject, Details, CommandLine, DestinationIp` | Combines fields from multiple Sysmon event types (process creation, network connection, registry) into one unified table. |
| `sort _time` | Orders every result chronologically, regardless of which event type produced it — this is what turns separate detections into a timeline. |

## Results

**26 of 143,183 events matched** — the combined filter is narrow enough to be reviewable by hand, despite drawing from a much larger overall dataset.

## Interpreting the Correlated Timeline

Bringing these events together, rather than viewing each query in isolation, reveals the actual shape of the incident:

- **Repeated, short-lived executions.** `Resume.exe` does not run once and persist — it is launched, runs briefly, and terminates, multiple times across more than a day (`09-16` through `09-18`). This pattern is more consistent with a user (or a script) re-opening the file repeatedly than with a single successful, continuously-running implant.
- **Execution and connection are tightly coupled.** Every `EventCode=3` network connection to `192.168.10.33:4444` observed in stage 05 lines up within seconds of an `EventCode=1` launch of `Resume.exe` — confirming that the network activity is a direct consequence of running this specific binary, not an unrelated background process.
- **The `Run`-key activity in this window belongs to Microsoft Edge, not the malicious binary.** The wildcard `TargetObject="*\\Run\\*"` filter was included specifically to catch persistence attempts, and it did surface `Run`-key writes in this timeframe — but attribution matters: the `Image` field on those events is `msedge.exe`, a legitimate, expected autostart entry, not `Resume.exe`. This reinforces the stage 06 finding that no persistence was established by the malicious binary in this run.
- **The story holds together without needing to assume anything.** Delivery (prior stages) → repeated execution → network beacon, each timestamped and attributable — is enough on its own to write a credible incident narrative, even with the persistence question answered as "not observed."

## Building the Narrative for a Report

A correlated timeline like this is what turns raw SPL output into the "Timeline of Events" section of an incident report. For this lab, that section would read approximately as:

> Between 2026-09-16 and 2026-09-18, the host executed `C:\Users\tejas\Downloads\Resume.exe` on at least four occasions. Each execution was short-lived (process termination observed seconds to tens of minutes later). On 2026-09-18 at 20:04:10, execution of the binary was immediately followed by an outbound TCP connection to `192.168.10.33:4444`, a non-standard, unassigned port on the internal lab segment. No registry-based persistence mechanism attributable to the binary was identified during the observation window; `Run`-key registry activity in the same timeframe was attributed to the legitimate Microsoft Edge auto-launch entry.

## Outcome

This stage demonstrates the core skill the whole lab builds toward:

1. Correlating multiple Sysmon event types (`1`, `3`, `5`, `12`, `13`) into a single chronological view using one SPL query.
2. Using that timeline to confirm causality (execution → connection) rather than just coincidence.
3. Correctly attributing ambiguous matches (the Edge `Run`-key activity) instead of assuming every hit on a broad filter is malicious — a critical skill for keeping false-positive rates manageable in real SOC work.

This timeline, together with the individual detections built in stages 02–06, forms the complete evidence base that would support an incident report — see [08. IR Playbook.md](08.%20IR%20Playbook.md) for how this translates into a response workflow.
